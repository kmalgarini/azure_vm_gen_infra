# Plan: DTR Artefact Cleanup (7-Day Retention)

## Overview

The restocking file generator writes artefact files into `/var/restocking/inbound/` on every timer tick (every 5 minutes). These files accumulate indefinitely. This plan introduces a scheduled cleanup that deletes artefacts older than **7 days**, keeping disk usage bounded and the directory from growing stale.

---

## Artefacts in Scope

All files in `/var/restocking/inbound/` are generated by the restocking lifecycle state machine. One DTR passes through up to six lifecycle stages, each producing one file:

| Stage | File pattern | Format |
|-------|-------------|--------|
| BCR batch (enrolment) | `BCR_<batch_id>_<ts>.txt` | Plain text |
| State 0 → 1 | `940_<dtr>_<ts>.xml` | XML (EDI 940) |
| State 1 → 2 | `ZRO_<dtr>_<ts>.txt` | Plain text |
| State 2 → 3 | `ZDN_<dtr>_<ts>.txt` | Plain text |
| State 3 → 4 | `945_<dtr>_<ts>.xml` | XML (EDI 945) |
| State 4 → retired | `945OSR_<dtr>_<ts>.xml` | XML (final) |

All filenames embed a UTC timestamp (`YYYYMMDDTHHMMSS`), so file-system mtime and filename agree.

**Files explicitly out of scope (must not be deleted):**

| Path | Purpose |
|------|---------|
| `/opt/app/generator_state.json` | In-memory counter and active-DTR registry — daily rolling, lives outside the inbound dir |
| `/var/jobs/*` | Job generator output — separate retention concern |

## Disk Growth Estimate

With default configuration (`restocking_dtrs_per_batch = 3`, timer every 5 minutes):

| Metric | Value |
|--------|-------|
| Ticks per day | 288 (12/hr × 24 hr) |
| Files per tick | 1 BCR + 3 DTRs × 5 lifecycle files = **16 files** |
| Files per day | ~4,600 |
| Avg file size | ~300–500 B |
| **Disk growth per day** | **~1.5–2.2 MB** |
| Steady-state at 7-day retention | **~10–15 MB** |
| Without any cleanup (1 year) | **~550–800 MB** |

The 7-day window keeps steady-state usage well under 100 MB even at higher `dtrs_per_batch` values.

---

## Retention Policy

- **Retention window**: 7 days (configurable via `RESTOCKING_ARTEFACT_RETENTION_DAYS` env var, defaulting to 7).
- **Target directory**: `RESTOCKING_INBOUND_DIR` (default `/var/restocking/inbound`).
- **File selection**: all regular files with mtime older than the retention window. No subdirectory recursion — the inbound dir is a flat directory.
- **Deletion**: immediate, hard delete. No archival.
- **Schedule**: daily at 02:00 UTC (off-peak, before the generator starts the day's first batch).

---

## Approach Options

### Option A — logrotate

logrotate is already used for `/var/jobs/events.jsonl`. It supports a `maxage` directive to purge old files.

**Pros**: no new unit files; already installed.

**Cons**: logrotate is designed for single log files or directories of log files with a consistent naming scheme. It does not support arbitrary flat-directory purges with mixed extensions (`.txt`, `.xml`). The `maxage` directive applies to the oldest rotated copy, not to individual files. **Not suitable for this use case.**

### Option B — cron

Add a cron entry for `appuser` that runs `find` daily.

**Pros**: simple one-liner.

**Cons**: cron requires the `cron` daemon to be installed and enabled (not guaranteed on minimal Ubuntu cloud images). systemd timers are the established pattern in this project (already used for the generators). Mixing both would be inconsistent.

### Option C — systemd oneshot service + daily timer ✓ recommended

Add a `dtr-cleanup.service` (oneshot) and `dtr-cleanup.timer` (daily at 02:00 UTC), using `find` to delete files older than 7 days. Inject both units via `cloud-init.yaml` using the same `write_files` + `runcmd` pattern already used for the generator units.

**Pros**:
- Consistent with the existing systemd-timer pattern
- Timer output is captured by journald (`journalctl -u dtr-cleanup`)
- `Persistent=true` ensures the cleanup runs even after a VM restart that missed the scheduled window
- Retention window is configurable via an env var in `/opt/app/.env`
- No new daemon or package required

**Cons**: two new unit files to maintain. Acceptable given the project already has four.

## Implementation Plan

### 1. New environment variable

Add `RESTOCKING_ARTEFACT_RETENTION_DAYS` to `/opt/app/.env` (via cloud-init `runcmd`) and to `terraform/variables.tf` so it can be tuned per environment.

Default value: `7`.

`.env` addition:
```ini
RESTOCKING_ARTEFACT_RETENTION_DAYS=7
```

### 2. New Terraform variable

```hcl
# terraform/variables.tf
variable "restocking_artefact_retention_days" {
  description = "Number of days to retain DTR artefact files in the restocking inbound directory before deletion."
  type        = number
  default     = 7

  validation {
    condition     = var.restocking_artefact_retention_days >= 1
    error_message = "restocking_artefact_retention_days must be >= 1."
  }
}
```

Pass the value through `cloud-init.yaml` as `${restocking_artefact_retention_days}`.

### 3. systemd unit files (cloud-init `write_files`)

**`/etc/systemd/system/dtr-cleanup.service`**

```ini
[Unit]
Description=Delete DTR artefact files older than retention window
After=network.target

[Service]
Type=oneshot
User=appuser
Group=appuser
EnvironmentFile=/opt/app/.env
ExecStart=/bin/bash -c '\
  find "$${RESTOCKING_INBOUND_DIR}" \
       -maxdepth 1 \
       -type f \
       -mtime +$${RESTOCKING_ARTEFACT_RETENTION_DAYS} \
       -delete \
  && echo "DTR cleanup complete"'
StandardOutput=journal
StandardError=journal
SyslogIdentifier=dtr-cleanup
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ReadWritePaths=/var/restocking
```

**`/etc/systemd/system/dtr-cleanup.timer`**

```ini
[Unit]
Description=Daily DTR artefact cleanup at 02:00 UTC
Requires=dtr-cleanup.service

[Timer]
OnCalendar=*-*-* 02:00:00 UTC
Persistent=true
AccuracySec=5m

[Install]
WantedBy=timers.target
```

### 4. cloud-init changes

In `scripts/cloud-init.yaml`:

- Add both unit files to `write_files` (same block as the existing generator units).
- Append to `runcmd`:
  ```yaml
  - systemctl enable dtr-cleanup.timer
  - systemctl start dtr-cleanup.timer
  ```
- Extend the `.env` `cat` block:
  ```
  RESTOCKING_ARTEFACT_RETENTION_DAYS=${restocking_artefact_retention_days}
  ```

### 5. `null_resource.wait_for_app` check

Extend the bootstrap verification remote-exec to confirm the new timer is active:

```hcl
# terraform/main.tf  — null_resource.wait_for_app
inline = [
  "cloud-init status --wait",
  "systemctl is-active app",
  "systemctl is-active restocking-generator.timer",
  "systemctl is-active job-status-generator.timer",
  "systemctl is-active dtr-cleanup.timer",  # ← add this
  ...
]
```

## Safety Considerations

| Risk | Mitigation |
|------|-----------|
| Deleting a file a downstream consumer hasn't processed yet | 7-day window is much longer than the maximum lifecycle duration (~30 min from BCR to 945OSR at 5-min ticks). Any file present after 7 days is either fully processed or permanently stale. |
| Cleanup deletes the state file | `generator_state.json` lives at `/opt/app/`, entirely outside the inbound dir. `find` targets `/var/restocking/inbound` with `-maxdepth 1` — the state file is unreachable. |
| Cleanup runs while the generator is mid-tick | Both are short-lived. The generator writes a complete file atomically (single `path.write_text` call). `find -delete` on a file that is being written would fail silently at worst. Files 7+ days old will never be mid-tick. |
| Timer disabled after VM restart | `Persistent=true` ensures the timer catches up and runs cleanup once the VM comes back online. |
| Cleanup produces no output / silent failure | All output goes to journald. Alert on `systemctl is-failed dtr-cleanup` to detect failed runs. |

## Verification

After implementation, verify with:

```bash
# Check timer is scheduled
systemctl status dtr-cleanup.timer
systemctl list-timers dtr-cleanup.timer

# Trigger a dry run manually (print files that would be deleted)
source /opt/app/.env
find "$RESTOCKING_INBOUND_DIR" \
  -maxdepth 1 -type f \
  -mtime +$RESTOCKING_ARTEFACT_RETENTION_DAYS

# Trigger a real run immediately (for testing)
sudo systemctl start dtr-cleanup.service
journalctl -u dtr-cleanup -n 20 --no-pager

# Confirm old files are gone
ls -lht /var/restocking/inbound/ | tail -20
```

## Out of Scope

- **Archival to Azure Blob Storage**: not required; artefacts are synthetic test data.
- **Job generator artefacts** (`/var/jobs/`): `events.jsonl` is already managed by logrotate (14-day rotation). `status.json` is an overwritten snapshot, not a growing file.
- **Compression before deletion**: files are small (<1 KB each); compression overhead is not justified.
- **Per-file-type retention**: all file types in the inbound directory represent the same logical lifecycle. A single retention window for all types is sufficient.
